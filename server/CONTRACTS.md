# Backend implementation boundary

This work implements the backend requested after the master guide. API keys remain blank. `POST /api/predict` runs Track A's trained survival model from `lifetwin/prediction/` (Root/Track B owns the route and inference adapter; Track A owns the artifacts). No training, death dates, comparison math, or sensitivity algorithm are in scope. Compare/sensitivity routes return HTTP 501 with `DeferredFeature` and null prediction/model fields; predict does too when the model files are missing.

Shared package: `server/lifetwin`. Imports use `lifetwin.*`. Shared Pydantic v2 types live in `lifetwin.core.models`: `ApiModel` (strict, extra fields forbidden), `HealthProfile` (partial metric fields), `ApiError`, `DeferredFeature`. Each module exports its own request/response types and `router: APIRouter`; all routes are prefixed `/api` by the application. Nested value objects do not need schema_version; top-level success objects include `schema_version: "1.0"`. Routes are stateless, with health data carried only in request/response context.

Ownership for the requested subagent work:

- Conversation worker owns `lifetwin/onboarding/` and `server/tests/test_onboarding.py`. Endpoint `POST /api/onboarding/turn`. Implement start/reply/confirm/correct/skip/cancel actions with explicit candidate versus confirmed profile, partial fields, unit clarification, correction, and mascot states. Keyless mode is an honest deterministic conversation guide, not a fake LLM. Optional provider extraction adapter uses explicit configuration/injection; absent provider returns usable guided text flow. Text and transcribed speech use the same contract; audio transport remains deferred.
- Check-ins (`lifetwin/checkin/`, `server/tests/test_checkin.py`): endpoints `POST /api/checkin/start` and `POST /api/checkin/turn`, not yet used by the app. Check-in history lives only on the phone: the caller sends `state.previous` every turn and the server stores nothing. Weekly answers return as `profile_update` (profile fields and units) for the app to apply and rerun the forecast; daily answers are history only. The emergency pause (`emergency: true`, action `resume`) is shared with onboarding through `onboarding/intents.py`. Check-in readings are question kinds and periods in the shared onboarding parser, not a fork of it.
- Coach (`lifetwin/coach/`, `server/tests/test_coach.py`): `POST /api/coach/plan`, not yet used by the app. Deterministic, cited daily plan with changes and a trace; the phone holds every plan and sends it back with feedback. Golden and red-team sets are in `server/tests/data/coach_*.json`. Card fields follow conversation-v2's `Recommendation`; the phraser follows its `personalize` interface so the two can merge. With `outside_ai_consent`, the phone builds `profile` from `outsideAiProfile()` (no wristband values); the provider itself only ever sees item drafts, never the profile. Rewording uses the shared `lifetwin.personalize` provider.
- Recommendations (`lifetwin/recommendations/`): `POST /api/recommendations`, stateless. Templates follow the lever order from `docs/model-sensitivity.json` (`levers.py`) and the on-device package's wellness-card sources. Outside-AI wording lives in `lifetwin/personalize/` (per-provider consent, output safety check, template fallback); it never decides values.
- Changes (`lifetwin/change/`, `server/tests/test_change.py`): endpoints `POST /api/change/start` and `POST /api/change/turn`, not yet used by the app. Saved answers have no edit fields; this conversation is the only way they change apart from onboarding, check-ins, Apple Health import with read-back and Delete my data. Experiment levers never call it. Stateless: the caller sends the confirmed profile and `memory_consent` each turn; confirmed values return as `profile_update` (the check-in shape), and a `habit_note` only with consent. It reuses the shared onboarding parser and intents through their public functions; the only parser additions are `weight_change()` and `someone_else()`. The held-out set `tests/data/change_heldout.json` was written before the module; `tests/change_eval.py` scores any set.
- Advisor worker owns `lifetwin/advisor/`, `lifetwin/research/` and corresponding tests. Endpoint `POST /api/advisor`. Implement cited, non-predictive educational planning and bounded topic-only research behind a Tavily adapter. Blank keys must yield a labeled curated/offline experience or explicit unavailable status; no external calls. No client-supplied predictions are accepted or simulated. Plans and supplements have unmodeled effects; no numerical longevity claims. Research may retrieve only configured/allowlisted public authorities through fixed provider endpoints, not arbitrary client URLs. Cite original sources for curated claims.
- Quiz worker owns `lifetwin/quiz/`, `server/content/` and `server/tests/test_quiz.py`. Endpoint `GET /api/quiz/questions` with versioned question/answer/explanation/source/game-effect data for local Flutter scoring. Include answer metadata intentionally for client-side/offline scoring, not a secure competitive quiz. No server health-profile mutation or durable quiz sessions. Curated questions must be sourced and reviewed. Optional detail route is okay; no model calls.
- Root owns app/config/errors/rate limits, the prediction route and inference adapter, deferred compare/sensitivity shells, packaging, contract exporter/checker/fixtures, CI, Docker and run docs; integrates all routers and tests.

Workers must not edit other workers' files, shared core/config, dependency files, docs or Git state. Tell root any required dependency or shared-interface change. Use `ApiError` shapes through `HTTPException` details if needed; root normalizes errors. Limit input lengths/collections and provider deadlines. Never log raw payloads, provider errors, keys, health values or transcripts. Do not read real secrets or make live provider calls. Tests use injected doubles or HTTPX mock transports.

The contract PR lands before dependent backend functionality merges. Workers may prepare modules concurrently; root stages only reviewed contract files for the first PR, then integrates feature modules in the backend PR. No worker should commit, switch branches, or merge independently in this shared checkout.
