The score remains Cox under the newer [#108 decision](https://github.com/ViktorOsadsky/lifetwin/issues/108); this work does not select or change a model.

## Result and remaining hardware dependency

This implements an explicit awake-posture minute contract, bounded transient raw-input processing seam, exact daily sitting aggregation, and a separate confirm-only `sedentary_min_day` suggestion, including a labelled built-in demo. **It does not implement a calibrated leg accelerometer classifier.** The repository contains no raw recording, axis/mount calibration or firmware classifier implementation to validate one. The real `lifetwin.band_day.v0` export has only combined `sitting_or_lying` and missing-position counts. It still produces **no awake-sitting suggestion**, even if someone declares its waking coverage complete. Do not close the raw-hardware derivation criterion from the synthetic labels alone.

NHANES PAD680 asks for sitting on a typical day and excludes sleep ([CDC 2017–March 2020 questionnaire documentation](https://wwwn.cdc.gov/Nchs/Data/Nhanes/Public/2017/DataFiles/P_PAQ.htm)). A dated observation is therefore read back with an explicit question about whether it is typical before it can become the person's usual-day answer. This source supports the distinction; it does not validate this hardware or the translation from sensor estimates to a questionnaire input.

To finish measured derivation, the hardware owner must provide an agreed raw stream/recording with timestamp and recorded time-zone semantics, sample rate, axis order/sign and units, mounting orientation, calibration, wear/quality information, and validated minute-level posture classification. Awake/asleep context and confirmation that the complete waking day was captured are separate required inputs. Thigh orientation alone is not a sleep classifier, and horizontal thigh orientation does not resolve all sitting/lying cases. The feature adapter supplies means and mean squared magnitude only; the hardware owner must establish whether those features suffice or replace that adapter with validated processing. No angle or activity thresholds were invented here.

## Additive interfaces

- `BandMinute.posture`: `unknown` (default), `sitting`, `standing`, `moving`, `lying`, or `sittingOrLying`. `wakeState`: `unknown` (default), `awake`, or `asleep`. Existing activity/minute APIs remain compatible; a step count or `moderate: false` never implies sitting.
- `processBandAccelerationMinute(...)`: consumes one minute's samples once, checks finite axes/timestamps and a 12,000-sample engineering capacity, then passes ephemeral mean-axis/magnitude features to a caller-supplied `BandPostureClassifier`. No classifier, no samples or non-wear returns unknown posture. Wake context defaults to unknown and is never inferred by this function. The returned `BandMinute` retains neither raw samples nor features; caller-owned acquisition buffers remain the caller's disposal responsibility. No logs, persistence or networking are added.
- `BandSittingRecording.fromMinutes(...)`: accepts at most 1,440 distinct minute-aligned records from one recorded calendar date and retains aggregate counts only. Duplicate civil minutes (including ambiguous repeated DST hours), cross-date input and fractional minute timestamps are rejected rather than fabricated. It counts only worn, explicitly awake, explicitly sitting minutes. Known sleep and known lying do not count as sitting. Unknown wake state, unknown/combined awake posture, or missing awake wear withholds the entire numeric suggestion; missing time never reduces a denominator or becomes zero.
- `completeWakingDay` defaults false. It is an explicit acquisition/confirmed-diary assertion that **all waking time** was captured, not an automatic consequence of elapsed wear, a sample count or the existing ten-hour activity rule. This layer cannot independently verify an upstream completeness assertion. No partial-day scaling is performed. An empty recording is unavailable; a complete known non-sitting waking day can yield a real zero.
- `BandStore.sittingDay(completeWakingDay: ...)` aggregates today's classified minute path. Existing v0 files contain no compatible minute labels and stay unavailable. The built-in recorded demo authors explicit synthetic awake/posture labels over its synthetic 8 AM–8 PM waking window; today's demo yields 688 sitting minutes. This is authored demo data, not four measured days or calibrated raw sensor output.
- `BandService.suggestSitting(recording, live: store.live, demo: store.demoOnly)`, `confirmSitting(...)`, `dismissSitting()` and `keepSitting()` are separate from the existing activity API. Synthetic data needs explicit demo opt-in, and measured data needs the live path. `BandSittingSuggestion.demo`, `sourceLabel` and the read-back distinguish **Demo data**. Imported synthetic v0 reports remain ineligible. Showing, dismissing or keeping an offer saves nothing. Sitting and activity have independent seven-day cooldowns.

The read-back names the recorded date/count and asks whether it is typical. Only `confirmSitting` calls the existing repository, changing `sedentary_min_day` with `source: wristband`, `estimated: true`; `outsideAiProfile()` excludes it. A replacement number the person supplies has their own Mochi provenance. Values outside the existing shared 0–1,439 entry range and stale read-backs after a saved sitting change are rejected. The existing activity field is not changed. A confirmed answer may reach the existing Cox assessment; no forecast calculations are implemented here.
