# Flutter: illustrated mobile UI

Use for actual Dart/Flutter deliverables. Keep the chosen art direction; MaterialApp is infrastructure, not a mandate to make stock cards. Verify current APIs against the installed SDK and matching primary documentation.

## Pick the smallest rendering system

- **Widgets** own readable text, layout, focus, routes, sheets, semantics and hit regions.
- **CustomPainter** suits original silhouettes, habitats and paths driven by a few app values. Keep its coordinates inside a bounded art region; do not paint the entire accessible UI as one image.
- **flutter_svg** suits reusable authored vector assets. Verify the exact SVG in Flutter: browser CSS, filters, masks and font behavior are not a promise of renderer parity. Prefer editable paths and presentation attributes. A compiler pass cannot establish visual fidelity.
- **Rive / Lottie** are optional for an authored rig or timeline with explicit input/state ownership. Validate the actual asset and runtime. They do not supply an original character for free.
- **Flame** is justified by a continuous world update, collisions, camera or many moving entities. Retain Flutter overlays for menus and accessible controls; preserve the game instance across builds. A pet home screen or reward map alone does not require an engine.

## Compose for constraints and touch

Let decorative scenery bleed to edges; protect controls and text with SafeArea. Use LayoutBuilder, Flexible, Wrap and intentional scrolling for the space actually available. Do not scale a complete fixed canvas or shrink all text with FittedBox. On narrow/short phones, reduce optional scenery, reflow status/actions, or scroll secondary content while retaining a useful character and primary action. Enlarged text grows its container and may change composition. Inspect the initial enlarged-text viewport before scrolling: if core actions disappear, rebalance header/art/control space or make the continuation visibly discoverable. A test calling ensureVisible proves reachability after scrolling, not a clear first view. Use TextScaler rather than assuming OS scaling is linear.

A custom button needs a stable hit region (48 logical pixels is a useful Android target; iOS guidance is 44), a visible affordance, a semantic action label and a distinct result. Move/compress its drawn face inside the stationary target. Restore on cancellation as well as release; commit on activation, then animate. For immediate-selection sheets, commit the choice and retain it on dismissal. For explicit Apply/Cancel sheets, keep a separate draft and discard it on cancellation; opening then dismissing without choosing leaves state unchanged. Repeated input must not duplicate rewards or lock the screen behind a long animation. Expose selected/disabled states and avoid duplicate art/parent semantics. If ExcludeSemantics removes a custom control’s descendant semantics, its outer Semantics must supply the activation action (such as onTap), not only a button label. Verify that a semantic activation produces the actual outcome; pointer taps alone cannot prove it.

Keep state in a clear owner shared by art, counts and selection. On spatial/scrolling scenes, exploration and selection are separate decisions: a persistent action must identify its current target. If that target is offscreen, reveal it before the local character response, or provide an equally clear persistent result; do not let a visible action animate an invisible selected object. A care action should change the appropriate need or visible character response; opening every control into the same snackbar does not demonstrate a game loop. Use local state for a visual study. Add backend, accounts or audio only when requested.

## Own animation and paint work

Use a small vocabulary: tactile press, coordinated reveal, character response. Create/dispose controllers in lifecycle; don't instantiate them in build. Pause idle loops offscreen. Prefer repaint listeners for paint-only changes; compare relevant fields in shouldRepaint and avoid needless full-scene rebuilds. Measure before claiming a performance improvement.

Read MediaQuery's disableAnimations preference and provide resolved content plus explicit state feedback. Stop ambient loops, particles and bobbing; merely shortening a repeating animation can cause flashing. When the preference changes while running, reconcile to the current state. Keep interruptions and successive actions coherent.

## Author native scroll motion when the journey calls for it

For an illustrated route map or collection journey, keep a real Flutter scrollable; use CustomScrollView/slivers when their layout behavior is useful. Bind a small, purposeful reveal or parallax to ScrollController position, with a defined subject, range, endpoint and reverse/reduced variant. Do not import web pinning distances or replace touch scrolling with a forced camera animation. Read scroll extents only after content dimensions exist, update mappings when layout changes, and dispose owned controllers. Preserve selection and hit regions while the art moves. Inspect the middle of the journey and return scroll as well as endpoints; useful destinations must remain discoverable without motion.

[ScrollController](https://api.flutter.dev/flutter/widgets/ScrollController-class.html) documents attachment/dimension timing; [CustomScrollView](https://api.flutter.dev/flutter/widgets/CustomScrollView-class.html) covers sliver composition and scroll semantics. These mechanics support an authored map; they are not a reason to animate a stationary pet home.

## Prove the actual Flutter slice

Run analyze and focused widget tests for meaningful state transitions. Capture the actual app/theme entrypoint with local fonts/assets loaded. A separate test MaterialApp can silently change sheet tint, typography, navigation or debug chrome; apply viewport/accessibility overrides around the real app instead of replacing its theme. Load icon-font families as well as text fonts, or use the actual authored drawings. Default widget-test Ahem boxes and missing-glyph squares are not a typography review. Set logical viewport, DPR, insets, text scaling and animation state explicitly; use bounded pumps for repeating motion. Suggested stress matrix: 320×693, 390×844 and 430×932 at normal and declared enlarged text. Adapt to the product's target devices rather than treating these as platform standards.

Capture an explicit painted phase, not merely a state assertion or a filename: a callback may update state before the next frame or while a sheet still covers the result. Verify the pressed frame visibly differs from idle and the reaction/result belongs to the asserted target. Inspect every capture, including a sheet/result state. Test press cancellation and rapid actions where relevant. Exercise the rendered runtime and inspect logs; widget goldens do not prove browser/native asset parity, physical-device performance or screen-reader usability. Report which runtime was actually checked. An HTML translation can be a sketch; it is not Flutter validation. A newly generated golden can preserve a bad design, so do not infer craft from passing comparisons.
