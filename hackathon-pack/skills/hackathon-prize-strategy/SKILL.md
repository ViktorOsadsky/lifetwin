# Prize strategy

Use current official event and sponsor sources. A prize list is volatile: date the evidence and recheck before submission. Prefer the supplied event URL, follow its actual client-rendered content when a text fetch shows loading, and cross-check official Devpost and sponsor briefs. Do not quietly substitute last year's Cal Hacks or the separate Berkeley AI Hackathon.

Read [the Cal Hacks snapshot](references/event-snapshot.md) only for this event. It records the evidence as of October 23, 2026 and does not settle later changes. Preserve conflicts, including cash-versus-hardware labels, TBD prizes, contradictory eligibility and timezone abbreviations.

For every track under consideration, record: challenge; sponsor tool required; judging weights; deliverables; entry gate; prize cash / gift card / crypto / credit / hardware / opportunity; per-team versus per-person; current access; and unresolved rule. “No explicit requirement in visible rubric” is different from “no requirement.” Qualifying for multiple tracks does not establish permission to stack awards.

Check the official hacking window and reuse/disclosure rules before copying preparation code or templates into the submission. The captured event listing says work must be done during the hackathon; a skill pack prepared beforehand is not proof that a submitted feature was built during permitted hours.

Choose one primary story and only genuinely useful integrations. Rank by demonstrated user need, achievable sponsor fit, working-demo clarity, accessible data/tools and build risk. Treat award value as one input. Unknown competitor counts mean win probability and expected cash are unknown. Use ordinal judgments or label scores as subjective; never invent odds or count multiple mutually exclusive placements as additive winnings.

Let hard gates override scores: inaccessible core data, no required sandbox, ineligible team, unfinished mandatory deliverable or unsafe/excessive critical path. A useful secondary sponsor should provide a needed layer, e.g. Apify for fresh evidence or Convex for durable shared state; adding two competing providers solely for logos weakens the product.

Map the chosen workflow to each rubric with visible proof. For Hyphenate, show a hireable finance seat and a hard exception. For Visa, make the shopping experience itself innovative and intuitive, then show trust. For Factory, its SDK must do work in the running product. For Bright Data, demonstrate real live public data and its failure handling; mocked demo data disqualifies the published challenge. For Figma, verify category-specific artifact/tool requirements before claiming that a polished webpage qualifies.

Return a ranked recommendation, exclusions and conditions, one project narrative, exact sponsor role and a requirement-to-artifact checklist. Mark the smallest next verification that could change the ranking. Do not submit, publish, register accounts or spend merely because a prize is attractive.

## Evaluate this skill

Given a prize headline labelled cash whose description is hardware, report hardware and the discrepancy. Given Apify top-five placements, recommend entering if useful but do not sum all placements into potential winnings. Given a beautiful static Figma mockup and a Factory prize, decline to claim Factory fit. Given Bright Data cached demo results, report ineligible under the visible live-data rule. Given a new missing-credential sponsor with a large award, show the access gate ahead of numerical score. Record the actual response and revise any failed decision.
