# Demo director

Start from the running product and the exact track rubric. Define the specific person, job and before/after result in one sentence. Open with the surprising useful action: a caught financial mistake, an impossible-looking constraint satisfied, or a graceful recovery. Explain the context after the judge sees the result. Show what the agent did and why, with evidence available in one click.

Use one complete flow. A Cal Hacks general judging slot is described on Devpost as three minutes plus two minutes of questions; some sponsors ask for a two-minute version. Prepare both. An example three-minute sequence: first 15 seconds show the moment; next 25 establish the user and stakes; 70 show one task and its source; 35 introduce a judge change or failure; 20 show measured proof and sponsor role; final 15 state the result and limitation. Adjust to the actual allotted slot and observed run time.

Show real/sandbox/simulated mode clearly. A retrieved source, model inference, locally simulated action and confirmed provider action are distinct. Never let an animation, invoice total, payment instruction or token enrollment imply that money moved. Report savings, accuracy and latency only with measured denominator and baseline; fixture performance is fixture performance.

## Rehearse the question that could break it

Keep a fresh held-out scenario. Change a model number, currency, deadline, line item, entity, evidence source or amount. Include a rate limit, missing source and timeout after submission. Watch for a correct refusal and an intelligible recovery. A demo that cannot tolerate any input change needs scope reduction or an explicit scripted limitation. Do not fake a judge's challenge with a predetermined result.

Run the actual route on the actual demo device, including cold load, reduced motion, screen sharing and reconnect. Check visible keyboard focus, readable source text and a direct path to reset the seeded job. Keep a recorded demo as backup, but do not represent replay as live. A fallback recording may satisfy general demo requirements yet fail a sponsor's live-data requirement.

## Package the submission

Check current deadline and timezone with the event: the captured Devpost says October 25 at 9 AM “PST,” while America/Los_Angeles is on daylight time then. Preserve the ambiguity and set an earlier internal freeze rather than claiming UTC from the abbreviation. Captured requirements include project image, code repository and demo; accepted/check-in status and presence at the venue are separate gates. Do not infer a solo exception from a solo prize while the listing also says teams of 2–4.

Prepare the title, one-sentence user benefit, screenshot, concise explanation, setup/env names, sponsor integration evidence, limitations, public links judges can open and source licenses. Use the repository's format. Keep secrets out of public artifacts. Do not publish or send without user authorization.

## Exercise and revise

Time a real walkthrough or record its actual action durations. Score whether a new viewer can identify user, transformation, evidence, sponsor contribution and one limitation. Compare the same opening before/after a revision; do not grade a script merely because it contains rubric words. Save a brief before/review/after record. Cut any screen or claim that the running product cannot substantiate.
