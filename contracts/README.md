# Backend contracts v1

The user requested non-prediction backend implementation with blank credentials. The Pydantic models in `server/lifetwin/` are the source for generated JSON schemas here. `schema_version` is `1.0`; breaking changes require a coordinated contract PR.

Run from the repository root after installing the project's dev dependencies:

```sh
uv sync --python 3.11
uv run python contracts/export.py --check
uv run python contracts/check.py
uv run python contracts/check.py --in-process
# Once the implementation server is running:
uv run python contracts/check.py --base-url http://127.0.0.1:8000
```

Regenerate schemas with `uv run python contracts/export.py` when approved types change; `--check` also fails on schema files that are no longer in `schema_registry.py`. Request schemas are exported in validation mode (defaulted fields are optional). Response schemas are exported in serialization mode, so every field the server always emits, including defaulted safety markers such as `status`, `prediction: null`, `voice_status` and `local_scoring`, is required. Offline mode checks the 19 schemas, 31 request fixtures and two static responses; it explicitly skips cases that require API replay. It does **not** claim to validate absent response fixtures. The 35 cases cover the success/deferred routes, a supported and an unsupported (age above 80) forecast, a single quiz question, invalid transitions, invalid inputs (feet typed as cm, unknown unit fields, out-of-range age), unsupported client fields, an ambiguous intake answer, a skipped field, unconfigured web research, invalid quiz limits, missing question versions, a missing voice consent and an unconfigured voice token route, a confirmed Apple Health import with and without values, and the drafted check-in routes (a daily start that mentions the last answer, a weekly "same as last week" read-back and its confirmation, confirming with nothing read back, an unknown script, an unknown check-in kind, a completed weekly check-in with its `profile_update`, and an emergency pause in onboarding and in a check-in with its resume).

Each request fixture states its schema result: `request_schema_valid: false` asserts the shared schema rejects it, and `request_schema_valid: true` on a 422 case pins a server-only rule (duplicate topics, reply without text, blank text) that the schema cannot yet express. In `response_subset`, `{"$each": {...}}` requires a nonempty list whose every element matches, for example every advisor action staying `unmodeled`.

Use `--in-process` to replay all 35 cases against a keyless app without opening a network socket; it explicitly clears provider configuration. Use `--base-url` for the same HTTP status/schema/semantic checks against a running keyless server. The two targets are mutually exclusive. Assertions check meaningful mode/error/game-state fields without copying the entire content bank. Neither mode establishes medical/model correctness or live provider access.

`POST /api/predict` returns `prediction.schema.json`: `status` `supported`/`unsupported`, survival at 1/3/5 years, a curve to `max_horizon_years` (5), `model_version`, the model inputs `filled_in` by the missing-value policy, a plain `reason` when unsupported, and `limitations`. Its fixtures pin the current trained model's numbers, so retraining updates them. It returns 501 `not_implemented` only when the model files are missing (see `server/README.md`). Compare and sensitivity intentionally return HTTP **501**, `status: not_implemented`, and null `prediction`/`model_version`. Input validation ranges describe accepted raw data only, not a validated prediction population. Comparison math, input gradients and fortune narration are left for later.

Check-ins (`POST /api/checkin/start`, `POST /api/checkin/turn`; `checkin.*.schema.json`): check-in history lives only on the phone (owner ruling), so the caller sends the previous answers in `state.previous` with every turn and the server stores nothing. Daily answers have their own names (`sleep_hours_last_night`, `exercise_minutes_today`, `alcohol_drinks_yesterday`) and are history only: they never change the profile. Weekly answers update the forecast: every response carries `profile_update`, a `HealthProfile` holding the confirmed weekly answers in the profile's own fields, units and ranges. When `complete` is true the app sets each non-null field of `profile_update` on the confirmed profile, leaves null fields as they are, and reruns the forecast; for a daily check-in `profile_update` is always empty. `wellbeing` (`good`, `okay`, `not_great`) is history only. Both conversations share one emergency check (`emergency()` in `onboarding/intents.py`): a reply that says something urgent is happening now (chest pain, can't breathe, having a heart attack or stroke, a fall and can't get up, wanting to die, bleeding that won't stop, asking for an ambulance) returns `emergency: true`, a `concerned` mascot event and only "I'm sorry you're going through that. If you need help right now, please call 911. We can carry on whenever you're ready." Nothing is taken and no next question is asked; the state is unchanged. The app shows a "Call 911" button the person taps themselves and "Continue", which sends action `resume` (a reply such as "let's carry on" works too) and repeats the same question or read-back. History and figures of speech ("my heart attack was in 2015", "I'm dying to see my grandkids", "this pain in my knee") are read normally. Conversation uses a stateless caller-held state, separate pending versus confirmed fields and explicit actions. Typed text and final speech transcripts share the path; voice capture/synthesis are deferred. Quiz delivery includes answer/scoring metadata for local offline play and never updates medical inputs. Advisor plans are educational and cited, with unmodeled effects. Blank provider keys must work without network calls.

Coach plan (`POST /api/coach/plan`; `coach.plan.*.schema.json`): Mochi's daily plan, stateless. The phone sends the confirmed `profile`, recent `checkins` (on-device `daily_logs` names plus `wellbeing`), `habit_notes` (used only when `memory_consent` is true), `goals`, `limits`, `movement_paused`, confirmed `readings` (blood pressure, A1c, LDL with unit, date and source; used only to notice trends and for the crisis line: at or above 180/120 returns `alert: bp_crisis`, a re-check and "contact your doctor now, or call 911 with symptoms", and pauses movement; never a diagnosis or a single-reading judgement, and never sent to a provider), the `previous_plan` it holds (its `revision_id`, `based_on`, `local_date`, `input_snapshot_id` and item refs, sent back unchanged) with per-item `feedback`, `latest_revision_id`, optional `said` (what the person just said) and `outside_ai_consent`. The response has 2-4 `items` (workout, diet, habit, encourage), each with `action_id`, `time_of_day`, `why`, `source_url` and accept/edit/dismiss `controls`, plus `changes` (one explanation per item), a replayable `trace` (facts, rule, evidence, action), `inputs` (snapshot id, observed/missing/stale; `experiments_used` is always false), `mood` for the twin and `memory_instruction` for the phone's notebook ("forget"/"forget_all", applied only after the person confirms). Items come only from the cited catalogue in `server/lifetwin/coach/catalog.py`. A previous plan that was altered, is not `latest_revision_id`, or whose feedback names another revision returns **409** `stale_revision`. The same snapshot on the same local day with nothing new returns the same revision (`reused_previous: true`). The emergency line returns `status: emergency` with no items. With `outside_ai_consent.muse`, Muse may reword item messages only; any line that fails the safety check puts every item back on its template (`phrased_by: templates`).

HTTP conventions for the implementation: 200 for usable non-predictive responses, 422 for invalid input, 404 for missing resources, 413 for oversized bodies, 429 for limits, 503/504 for unavailable/timed-out dependencies, and 501 for intentionally deferred model features. Error bodies use `error.schema.json` and exclude raw inputs/provider details. `server/CONTRACTS.md` defines module ownership.
