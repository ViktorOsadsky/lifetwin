# Backend contracts v1

The user requested non-prediction backend implementation with blank credentials. The Pydantic models in `server/lifetwin/` are the source for generated JSON schemas here. `schema_version` is `1.0`; breaking changes require a coordinated contract PR.

Run from the repository root after installing the project's dev dependencies:

```sh
uv sync --python 3.11
uv run python contracts/export.py --check
uv run python contracts/check.py
uv run python contracts/check.py --in-process
# Once the implementation server is running:
uv run python contracts/check.py --base-url http://127.0.0.1:8000
```

Regenerate schemas with `uv run python contracts/export.py` when approved types change; `--check` also fails on schema files that are no longer in `schema_registry.py`. Request schemas are exported in validation mode (defaulted fields are optional). Response schemas are exported in serialization mode, so every field the server always emits, including defaulted safety markers such as `status`, `prediction: null`, `voice_status` and `local_scoring`, is required. Offline mode checks the 22 schemas, 46 request fixtures and two static responses; it explicitly skips cases that require API replay. It does **not** claim to validate absent response fixtures. The 50 cases cover the success/deferred routes, a supported and an unsupported (age above 80) forecast, a single quiz question, invalid transitions, invalid inputs (feet typed as cm, unknown unit fields, out-of-range age), unsupported client fields, an ambiguous intake answer, a skipped field, unconfigured web research, invalid quiz limits, missing question versions, a missing voice consent and an unconfigured voice token route, a confirmed Apple Health import with and without values, and the drafted check-in routes (a daily start that mentions the last answer, a weekly "same as last week" read-back and its confirmation, confirming with nothing read back, an unknown script, an unknown check-in kind, a completed weekly check-in with its `profile_update`, and an emergency pause in onboarding and in a check-in with its resume), and the change conversation (a free start and a start on one answer, a free answer read back, a big jump double-checked, a confirmed `profile_update`, the probe and the habit note with memory consent, an age change of more than a birthday, a refused sex-at-birth change, the doctor question for diabetes, an emergency pause and its resume, confirming with nothing read back, an inconsistent state and `diastolic_bp` as a field).

Each request fixture states its schema result: `request_schema_valid: false` asserts the shared schema rejects it, and `request_schema_valid: true` on a 422 case pins a server-only rule (duplicate topics, reply without text, blank text) that the schema cannot yet express. In `response_subset`, `{"$each": {...}}` requires a nonempty list whose every element matches, for example every advisor action staying `unmodeled`.

Use `--in-process` to replay all 50 cases against a keyless app without opening a network socket; it explicitly clears provider configuration. Use `--base-url` for the same HTTP status/schema/semantic checks against a running keyless server. The two targets are mutually exclusive. Assertions check meaningful mode/error/game-state fields without copying the entire content bank. Neither mode establishes medical/model correctness or live provider access.

`POST /api/predict` returns `prediction.schema.json`: `status` `supported`/`unsupported`, survival at 1/3/5 years, a curve to `max_horizon_years` (5), `model_version`, the model inputs `filled_in` by the missing-value policy, a plain `reason` when unsupported, and `limitations`. Its fixtures pin the current trained model's numbers, so retraining updates them. It returns 501 `not_implemented` only when the model files are missing (see `server/README.md`). Compare and sensitivity intentionally return HTTP **501**, `status: not_implemented`, and null `prediction`/`model_version`. Input validation ranges describe accepted raw data only, not a validated prediction population. Comparison math, input gradients and fortune narration are left for later.

Check-ins (`POST /api/checkin/start`, `POST /api/checkin/turn`; `checkin.*.schema.json`): check-in history lives only on the phone (owner ruling), so the caller sends the previous answers in `state.previous` with every turn and the server stores nothing. Daily answers have their own names (`sleep_hours_last_night`, `exercise_minutes_today`, `alcohol_drinks_yesterday`) and are history only: they never change the profile. Weekly answers update the forecast: every response carries `profile_update`, a `HealthProfile` holding the confirmed weekly answers in the profile's own fields, units and ranges. When `complete` is true the app sets each non-null field of `profile_update` on the confirmed profile, leaves null fields as they are, and reruns the forecast; for a daily check-in `profile_update` is always empty. `wellbeing` (`good`, `okay`, `not_great`) is history only. Both conversations share one emergency check (`emergency()` in `onboarding/intents.py`): a reply that says something urgent is happening now (chest pain, can't breathe, having a heart attack or stroke, a fall and can't get up, wanting to die, bleeding that won't stop, asking for an ambulance) returns `emergency: true`, a `concerned` mascot event and only "I'm sorry you're going through that. If you need help right now, please call 911. We can carry on whenever you're ready." Nothing is taken and no next question is asked; the state is unchanged. The app shows a "Call 911" button the person taps themselves and "Continue", which sends action `resume` (a reply such as "let's carry on" works too) and repeats the same question or read-back. History and figures of speech ("my heart attack was in 2015", "I'm dying to see my grandkids", "this pain in my knee") are read normally. Conversation uses a stateless caller-held state, separate pending versus confirmed fields and explicit actions. Typed text and final speech transcripts share the path; voice capture/synthesis are deferred. Quiz delivery includes answer/scoring metadata for local offline play and never updates medical inputs. Advisor plans are educational and cited, with unmodeled effects. Blank provider keys must work without network calls.

Changes (`POST /api/change/start`, `POST /api/change/turn`; `change.*.schema.json`): the app has no edit fields for saved answers (owner ruling: people consult their agent before their things change). "Change" or "Update" opens this conversation instead. Apart from onboarding, check-ins, an Apple Health import with read-back and "Delete my data", it is the only way a saved answer changes; experiment levers never call it, because they change only the experimental copy of the profile. It is stateless: the caller sends the confirmed `profile` and `memory_consent` with every turn, plus the returned `state`, and the server stores and logs nothing. Start with `field` (any profile field except `diastolic_bp`; blood pressure is one reading under `systolic_bp`) or none ("What would you like to update?", answered freely: "I lost some weight", "I quit smoking"). Mochi says the current value, asks what changed, reads the new value back and saves only after a yes (or action `confirm`). A big jump gets a gentle double-check ("That's quite a change from 160 to 120 pounds. Is 120 right?"); values outside the onboarding bounds are never read. Age moves only up by one birthday; sex at birth cannot change once saved (a blank one may be filled in); diabetes is added or corrected only after Mochi asks whether a doctor said so, and is never inferred. "I don't know", "never mind" and the same value change nothing; someone else's values are refused; corrections, chatter filtering, control replies and the emergency pause work as in onboarding. With `memory_consent: true`, Mochi may ask one gentle probe ("Did something change, like a new routine?") and returns the answer as `habit_note` (`field`, `text`, the person's words) with the saved change. When `complete` is true, the app sets each non-null field of `profile_update` (the check-in shape) on the confirmed profile and reruns the forecast; an empty `profile_update` means nothing changed. A conversation may go on after `complete` (another answer the person mentioned); each later complete response carries only its own change.

HTTP conventions for the implementation: 200 for usable non-predictive responses, 422 for invalid input, 404 for missing resources, 413 for oversized bodies, 429 for limits, 503/504 for unavailable/timed-out dependencies, and 501 for intentionally deferred model features. Error bodies use `error.schema.json` and exclude raw inputs/provider details. `server/CONTRACTS.md` defines module ownership.
